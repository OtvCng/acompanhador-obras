## 1. O que sobe

| Serviço | Imagem | Para quê |
| --- | --- | --- |
| `db` | `postgres:16-alpine` | Banco. Dados no volume `obras-db` (sobrevive a redeploy). |
| `api` | `Dockerfile --target api` | API Node (Fastify). Aplica as migrations sozinha ao iniciar (`MIGRAR_AO_INICIAR=true`). Porta interna 3333. |
| `web` | `Dockerfile --target web` | nginx: serve o front e encaminha `/api/*` para a `api`. É o único serviço exposto (porta 80 no container; `8080` no teste local). |

Front e API ficam na mesma origem, então o cookie de sessão funciona sem CORS.

## 2. Variáveis de ambiente

Cadastrar no Coolify (nunca no git). Modelo em `.env.example` na raiz.

| Variável | Obrigatória | O que é |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | sim | Senha do Postgres. Gerar uma longa e aleatória. |
| `COOKIE_SECURE` | não (padrão `true`) | `true` com HTTPS (produção). `false` só em teste local via http. |
| `ADMIN_NOME`, `ADMIN_EMAIL` | para o primeiro acesso | Diretor criado pelo setup. |
| `ADMIN_SENHA` | não | Vazio = o setup gera uma senha e imprime uma vez no log. |

## 3. Testar local antes

Pré-requisito: Docker Desktop rodando.

```bash
cp .env.example .env            # e troque POSTGRES_PASSWORD; COOKIE_SECURE=false para http://localhost
docker compose up -d --build    # http://localhost:8080
docker compose exec api node dist/setup.js      # cria o diretor (só na primeira vez)
docker compose exec api node dist/exemplos.js   # opcional: 6 obras de demonstração
docker compose down             # derruba (o volume com os dados fica)
docker compose down -v          # derruba E APAGA o banco
```

### 3.1 Teste de produção isolado (feito em 2026-11-10, terminal Fundação)

Rodado lado a lado com o ambiente de dev sem encostar nele: projeto Compose separado (`-p`) e arquivo de variáveis próprio (`--env-file`), então rede, containers e volume (`obras-prodteste_obras-db`) são outros.

```bash
docker compose -p obras-prodteste --env-file <arquivo.env> -f docker-compose.yml up -d --build
docker compose -p obras-prodteste --env-file <arquivo.env> exec -T api node dist/setup.js
docker compose -p obras-prodteste --env-file <arquivo.env> down -v
```

Resultado (tudo passou):

| Checagem | Resultado |
| --- | --- |
| `GET /healthz` (nginx) | 200 `ok` |
| `GET /api/saude` (via nginx → api) | 200 `{"ok":true}`; log da api: `Migrations aplicadas (/app/drizzle)` ao subir |
| `GET /api/obras` sem login | 401 |
| `node dist/setup.js` | `Diretor criado: ...` + `Senha gerada (anote, não aparece de novo): ...` |
| Login do diretor (`POST /api/auth/login`) | 200, cookie `sid` httpOnly |
| `GET /api/obras` logado | 200 `[]` (banco novo); após `POST /api/exemplos`, 6 obras |
| Front: `/`, rota profunda `/obras/xyz`, bundle JS | 200 / 200 (fallback SPA) / 200 |
| Permissões (engenheiro e encarregado criados pela API) | encarregado vê só a obra dele com R$ convertidos em pesos (orçamento = 100), 404 em obra alheia, 403 em PUT e DELETE; engenheiro vê só a dele (com R$), 404 em obra alheia, 403 em DELETE e em trocar o engenheiro responsável; DELETE pelo diretor 200 |

O que aprendemos:

- **O compose NÃO cria o diretor.** Ao subir, a `api` só aplica as migrations. O diretor nasce quando alguém roda `node dist/setup.js` dentro do container `api`, que lê `ADMIN_NOME`, `ADMIN_EMAIL` e `ADMIN_SENHA` do ambiente **do container** (o que estava no `.env` na hora do `up`). Sem `ADMIN_EMAIL` o setup falha. Se já existir algum usuário com senha, ele não cria nada (pode rodar de novo sem medo). Mudou o `.env` depois? Recrie a `api` (`up -d api`) antes do setup.
- **Sem `--env-file`, o Compose lê o `.env` da raiz automaticamente** (e o `POSTGRES_PASSWORD` é obrigatório: `${POSTGRES_PASSWORD:?...}`). Para testes paralelos use um arquivo à parte e passe o mesmo `-p`/`--env-file` em todos os comandos (`up`, `exec`, `down`).
- **`COOKIE_SECURE=true` em http quebra o login em silêncio:** o login responde 200, mas o navegador descarta o cookie `Secure` e a próxima chamada dá 401. Em teste local via `http://localhost:8080`, use `false`; em produção (HTTPS), `true`.
- As imagens têm tag fixa (`acompanhador-obras-api:local`, `acompanhador-obras-web:local`), compartilhada entre projetos Compose: um build num projeto sobrescreve a tag do outro. Sem impacto no Coolify.
- Build do front avisa bundle de ~945 kB (276 kB gzip). Não bloqueia; code-splitting fica para depois.

## 4. Passo a passo no Coolify

### 4.1 Pré-requisitos

1. Servidor com o Coolify instalado.
2. **O repositório num Git que o Coolify alcance** (GitHub, GitLab, Gitea...). Hoje o repo é só local (Q22): criar o remoto é decisão do Otavio. Repo privado precisa de acesso (GitHub App ou deploy key; conferir na versão do Coolify instalada).
3. Domínio ou subdomínio com DNS tipo A apontando para o servidor, para ter HTTPS.

### 4.2 Criar o recurso

1. Novo recurso a partir do repositório Git, build pack **Docker Compose**, arquivo `/docker-compose.yml`.
2. Cadastrar as variáveis da seção 2.
3. Domínio: associar ao serviço **`web`**, porta **80**, com `https://` na frente (ex.: `https://obras.seudominio.com.br`). O Coolify emite o certificado quando o DNS já aponta para o servidor (conferir na versão do Coolify instalada).
4. A porta `8080:80` do compose serve para teste local. No Coolify o proxy dele encaminha o domínio para o container; se a porta publicada no host conflitar, remova o bloco `ports` do serviço `web` (conferir na versão do Coolify instalada).
5. `db` e `api` não precisam de domínio nem de porta pública.

### 4.3 Primeiro deploy

1. Disparar o deploy e acompanhar o log. A primeira build leva alguns minutos (`pnpm install` + build do front e da API).
2. Abrir o terminal do container `api` pelo Coolify (ou `docker exec` no servidor) e rodar `node dist/setup.js`. Anote a senha impressa se `ADMIN_SENHA` estiver vazio.
3. Entrar com o e-mail do diretor, ir em **Usuários** e cadastrar engenheiros e encarregados.

### 4.4 Redeploy

- Redeploy (manual ou por webhook) recria `api` e `web`; o volume do `db` continua. Migrations novas rodam sozinhas quando a `api` sobe.
- **Nunca** apague o volume `obras-db` sem backup.

## 5. Cuidados

- **Backup do Postgres:** configure no Coolify (ele tem backup agendado para bancos; conferir se vale para um `db` dentro de um compose na versão instalada) ou um `pg_dump` diário por cron no servidor. Sem backup, perder o servidor é perder os dados.
- **Senha esquecida:** o diretor redefine em Usuários. Se o próprio diretor perder o acesso: `node dist/criar-usuario.js --email <email> --perfil diretor` no container `api` redefine a senha e imprime a nova.
- **Fotos:** os apontamentos ainda guardam só o nome da foto (fake). Upload real precisa de armazenamento (volume ou S3 compatível), que fica para um próximo passo.
- **Robôs:** o app não tem conteúdo público; um `robots.txt` em `apps/web/public` é um ajuste futuro.
