## 1. O que o app é hoje (LEIA ANTES DE PUBLICAR)

O Acompanhador de Obras, nesta fase, é **só um front-end estático** (React + Vite) servido por nginx.

> **Não existe backend, banco de dados nem login real.**
>
> - Todos os dados (obras, apontamentos, baselines, modelos editados) ficam no **localStorage do navegador de cada pessoa** (chaves `obras:v1` e `obras:modelos:v1`).
> - **Cada pessoa vê só os próprios dados.** Se o diretor lança um apontamento no computador dele, o engenheiro **não** vê esse apontamento no celular dele. Não há sincronização nenhuma.
> - **Os dados somem** se a pessoa limpar o navegador, usar aba anônima, trocar de navegador ou de aparelho.
> - O seletor de usuário no topo (Diretor / Engenheiro / Encarregado) é **simulação**: qualquer pessoa com o link escolhe qualquer perfil. Não serve como controle de acesso.
> - As 6 obras que aparecem ao abrir são **fictícias** (dados de exemplo). O botão "Restaurar dados de exemplo" volta a elas.
>
> Ou seja: publicar hoje serve para **demonstrar e validar o formato** (com o Otavio e o sogro), não para uso real na construtora. Não coloque dados reais de obra, cliente ou valor achando que estão guardados.

Como qualquer pessoa com a URL abre o app, vale publicar num domínio não divulgado ou atrás de uma proteção básica (ver seção 5).

## 2. Arquivos de deploy no repositório

| Arquivo | Para quê |
|---|---|
| `Dockerfile` | Multi-stage. Estágio 1: `node:22-alpine` + corepack (pnpm 9.0.0), `pnpm install --frozen-lockfile`, `pnpm --filter @obras/web build`. Estágio 2: `nginx:1.27-alpine` servindo `apps/web/dist`. |
| `docker/nginx.conf` | Fallback de SPA (`try_files ... /index.html`), cache longo e imutável em `/assets/`, sem cache em `index.html`, gzip, endpoint `/healthz`. |
| `.dockerignore` | Deixa fora `node_modules`, `dist`, `.turbo`, `.git`, `docs` (inclui os briefings), `apps/api`, testes. |
| `docker-compose.yml` | Serviço `web`, porta `8080 -> 80`, healthcheck em `/healthz`. |

Observação: o `package.json` da raiz força o rollup para `@rollup/wasm-node` (o Windows desta máquina bloqueou o binário nativo). No Linux do container isso também funciona e foi mantido.

## 3. Testar local antes

Pré-requisito: Docker instalado e rodando (Docker Desktop no Windows).

```bash
docker compose up --build        # sobe em http://localhost:8080
curl -i http://localhost:8080/healthz          # deve responder 200 "ok"
curl -i http://localhost:8080/obras            # rota da SPA: 200 com o index.html
docker compose down              # derruba
```

Sem Docker, dá para conferir só o build do front: `pnpm --filter @obras/web build` (gera `apps/web/dist`).

## 4. Passo a passo no Coolify

### 4.1 Pré-requisitos

1. Um servidor com o Coolify instalado e funcionando.
2. **O repositório precisa estar num Git que o Coolify alcance** (GitHub, GitLab, Gitea etc.). Hoje o repo é só local (decisão Q22): criar o remoto é um passo à parte, que o Otavio decide. Se for repositório privado, o Coolify precisa de acesso (GitHub App ou deploy key; conferir na versão do Coolify instalada).
3. Um domínio (ou subdomínio) com registro DNS do tipo A apontando para o IP do servidor do Coolify, se quiser HTTPS com domínio próprio.

### 4.2 Criar o recurso

1. No Coolify, dentro de um projeto/ambiente, adicionar um novo recurso a partir de um repositório Git (público ou privado, conforme o caso).
2. Informar a URL do repositório e o branch (o branch de trabalho hoje é `master`; o principal previsto é `main`).
3. Escolher o **build pack**. Duas opções, ambas funcionam:
   - **Dockerfile** (recomendado, mais simples): Dockerfile na raiz (`/Dockerfile`), contexto de build na raiz do repo.
   - **Docker Compose**: apontar para `/docker-compose.yml`. Nesse modo o Coolify lê o serviço `web`.
   - Os nomes exatos dos campos: conferir na versão do Coolify instalada.
4. **Porta:** o container escuta na **80** (é a porta exposta pelo nginx). No modo Dockerfile, informar 80 como porta exposta. O mapeamento `8080:80` do compose é só para teste local; no Coolify o proxy dele (Traefik ou Caddy, conforme a versão) encaminha o domínio para a porta do container, então em geral não é preciso publicar porta no host (conferir na versão do Coolify instalada).
5. **Healthcheck:** o container já tem `HEALTHCHECK` no Dockerfile (`/healthz`). Se o Coolify pedir um caminho de healthcheck, usar `/healthz` na porta 80.
6. **Variáveis de ambiente:** nenhuma é necessária hoje.

### 4.3 Domínio e HTTPS

1. No recurso, preencher o domínio com `https://` na frente (ex.: `https://obras.seudominio.com.br`). O Coolify costuma emitir o certificado Let's Encrypt sozinho quando o domínio usa `https://` e o DNS já aponta para o servidor (conferir na versão do Coolify instalada).
2. Sem domínio próprio, o Coolify pode gerar um domínio de teste; conferir na versão do Coolify instalada.

### 4.4 Deploy e redeploy

1. Disparar o deploy pelo botão de deploy do recurso e acompanhar o log de build: o estágio de `pnpm install` + `vite build` leva alguns minutos na primeira vez.
2. Depois de no ar, testar: a página inicial, uma rota interna direto na barra de endereço (ex.: `/obras`) para conferir o fallback de SPA, e `/healthz`.
3. **Redeploy:** a cada push no branch configurado, dá para redeployar manualmente pelo botão ou ativar deploy automático por webhook (conferir na versão do Coolify instalada).
4. **Atenção:** um redeploy **não apaga** os dados de ninguém, porque eles estão no navegador de cada um, não no servidor. Pelo mesmo motivo, apagar o recurso no Coolify também não recupera nem remove dados.

## 5. Cuidados enquanto não houver backend

- Qualquer pessoa com a URL entra e escolhe qualquer perfil. Se quiser restringir a demo, proteger com autenticação básica no proxy do Coolify (conferir na versão do Coolify instalada se há opção de basic auth para o recurso) ou não divulgar o domínio.
- Não indexar: o app não tem conteúdo público. Se necessário, adicionar um `robots.txt` em `apps/web/public` numa entrega futura (dono: telas/orquestrador).
- Se a estrutura dos dados mudar, a versão da chave (`obras:v1`) sobe e os navegadores voltam ao seed automaticamente; quem tinha dados locais perde esses dados.

## 6. O que muda quando tiver backend (fase 2)

- Entra o serviço `apps/api` (reservado no monorepo) e um banco (ex.: PostgreSQL). O `docker-compose.yml` ganha os serviços `api` e `db` com volume persistente, e o Coolify passa a usar o build pack Docker Compose (ou recursos separados para front, API e banco).
- O store do front troca o localStorage por chamadas HTTP (os hooks `useObras`, `useObra` etc. são o contrato e as telas não precisam mudar).
- Login real com perfis (Diretor, Engenheiro, Encarregado) validados no servidor, e o seletor de usuário simulado sai.
- Variáveis de ambiente passam a existir (URL da API, credenciais do banco, segredo de sessão), cadastradas no Coolify e nunca no Git.
- Backup do banco (o Coolify tem recurso de backup para bancos gerenciados por ele; conferir na versão do Coolify instalada).
- Fotos dos apontamentos (hoje nomes fake) passam a precisar de armazenamento de arquivos (volume ou S3 compatível).
- O nginx pode continuar servindo o front e fazer proxy de `/api` para o backend, ou o Coolify roteia por domínio/caminho.
